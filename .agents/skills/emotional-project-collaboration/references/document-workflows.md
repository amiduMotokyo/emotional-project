# 需求、创新、实验与论文流程

按任务选择对应段落，无需为每次工作创建四类文档。优先更新现有主题文件；日期前缀可用于独立实验或调研记录，不强制每次修改另建版本。

## 需求理解或变更

位置：docs/<负责人>/requirements/。

建议内容：

```markdown
# 主题
状态：分析中 / 提议 / 已采用 / 已替代
对应模块：
题目依据：原文件及对应章节

## 现状与问题
当前实现或数据证据；区分题目要求与个人理解。

## 调整方案
具体变化、原因、兼容性与受影响模块。

## 验证与交接
如何判断完成、需要更新哪些调用方和文档。

## 结论
已确定的内容、依据与仍待解决的问题。
```

“已采用”应有用户指令或当前授权范围内实际确定并实施的依据，不单靠文档作者写入状态。无需将常规实现决策升级为等待组员批准的流程。跨组结论同步公共约定，详细推导只维护一份。

## 创新点与文献调研

位置：docs/<负责人>/research/。

围绕实际模块组织：待解决现象、基线局限、候选方法、与基线的区别、数据及计算成本、最小验证实验、预期失败条件。引用来源应能定位到论文或官方资料，未检索核实的文献不得编造。

创新点分为“候选假设”“已实现待验证”“实验支持”“未支持或放弃”等状态。说明在本题中的改进不等于声称学术首次。三天时间内优先验证一个有明确对照的改进，是否扩展实验取决于用户任务和当前进度，不固定强制数量。

例如：C提出按连续片段长度调整缺失训练策略，文档应放docs/C/research，而不是放docs根目录；如果随后需要修改B的输入掩码接口，修改原B实现并同步契约，不复制B的数据加载器。

## 实验记录

位置：可阅读记录放docs/<负责人>/experiments；日志和权重放<负责人>/outputs。

一项实际实验至少记录：

- 目标或待验证假设，与哪个基线比较。
- 数据版本、划分、样本处理和缺失设置。
- 配置文件、种子、代码版本（若可用）、环境与关键依赖。
- 实际运行入口、运行状态、产物位置。
- 指标定义与结果，必要的耗时和资源信息。
- 结果支持什么、不支持什么，异常与下一步。

未运行只记录实验计划，不填入虚构指标。中断实验记录实际完成范围；不使用无标签专项集计算准确率。对外引用的图表保留数据来源与生成方式，需长期保留的图片放文档assets中。

## 论文写作与合并

位置：各组docs/<负责人>/paper；合并稿docs/A/paper。

模块作者交付：输入与符号定义、方法及必要公式、实现参数、实际实验、图表说明、结论与局限。A统一章节衔接、重复定义、图表编号和参考文献，不替代模块作者凭代码补造论证。

写作时检查：

- 公式符号与实现、张量维度相符。
- 结果数值可追溯到实验记录，图表标题包含必要条件。
- 基线与改进使用可比的数据划分和指标。
- 问题1全量100条结果及至少一个对齐案例齐备。
- 问题2说明缺失类型、位置、时长影响及专项预测。
- 问题3提供模态贡献、主要参考模态、局部证据和核查依据。
- 方法设计、实验观察与原因推测区分表述。

总计划中的3天节点用于安排工作，不视为自动执行命令：第1天方法正文，第2天完整初稿，第3天结果锁定与统稿。修改工期时保留明确的写作和最终检查时段，不将论文写作假定为不占时间。

## 完成示例

- 用户让B分析解释创新：更新docs/B/research的对应文档，说明候选与验证方法；不自动训练所有模型。
- 用户让C修复MAE计算：修改C维护的评估实现，检查实际调用方，做适当验证；不另建B版评估器。
- 用户让A整理已有问题1结果：检查100条覆盖及时间映射，更新docs/A/experiments或paper，特征仍留A/outputs。
- 用户让全组统一接口：维护者修改各自模块，公共约定记录跨组决策，各组详细记录留在所属文档目录。
